Network access for CI/CD that's exactly enough, and no more.

SkiMasque gives a CI/CD job exactly the network access it needs, and nothing else, only for as long as it needs it. No broad VPN and no standing credentials. Each tunnel is short-lived, tied to the job's identity, and denied by default.

The problem

CI network access is too broad and lasts too long.

SkiMasque replaces this with a policy over workload identity. The tunnel opens only when that policy allows it, and closes when the job ends.

✗

A CI job that needs one database gets a VPN that reaches your whole network.

✗

Static credentials in CI secrets don't expire and are hard to rotate.

✗

IP allowlists say where from, never who or which workflow.

✗

"Temporary" access is rarely torn down.

✗

Different repos and workflows need different access, and that's tedious to express with any of the above.

How it works

Who, what, where, and for how long.

A workload proves who it is, declares what it is running, and asks to reach a destination. A policy decides. If no rule allows the request, it is denied.

WHO

Workload identity

A GitHub Actions job proves its repository, workflow, and branch with an OIDC token. GitLab, Buildkite, and generic OIDC are supported too.

WHAT

Application

The job declares what it is running, such as terraform or psql. Rules are scoped to that application.

WHERE

Destination

An exact host, a *.suffix wildcard, an IP, a CIDR, or *, each with an exact port, a range, or *.

LIMITS

Time and rate

Maximum session length, bandwidth, packets per second, connection count, and byte caps. When the job ends, access ends.

Quick start

Three steps, and no infrastructure to run.

Point CI at SkiMasque Cloud, write a policy, and add one step to your workflow. Full walkthrough →

Sign in and create an org

The GitHub device flow signs you in to SkiMasque Cloud.

$ skimasque login
$ skimasque org create "Acme"

Write a policy and test it locally

skimasque init scaffolds a policy. Its tests run offline and fit in CI.

$ skimasque policy test
production
  ok   psql -> db.internal:5432      (expect allow)
  ok   psql -> secrets.internal:443  (expect deny)

Wire the workflow

The action exchanges the runner's OIDC token for a short-lived credential and sets ALL_PROXY to a local SOCKS5 relay. Tools that honour ALL_PROXY (terraform, psql, curl, git, most cloud SDKs) can then reach only what your policy allows.

.github/workflows/deploy.yml
permissions:
  id-token: write          # the job mints its own OIDC token
  contents: read

steps:
  - uses: skimasque-dev/connect@v1
    with:
      proxy: gateway.skimasque.com:443
      audience: https://gateway.skimasque.com
      application: terraform

  - run: terraform apply -auto-approve   # egresses through the gateway

Policy as code

Readable policies you can test and diff.

The policy engine does no I/O. It takes a request and returns a decision, so policies can be reviewed, diffed, and tested in CI like any other code. Write them in TOML or YAML. When a request is denied, the engine says why and suggests a rule.

.masque/policies/production.toml
name = "production"

[match]                       # WHO
repository = "acme/widget"
branch = "main"

[[rules]]
application = "terraform"     # WHAT
action = "allow"
destinations = [              # WHERE
    "api.production.example.com:443",
    "*.terraform.io:443",
]

[session]                     # LIMITS
max_duration = "20m"
[limits]
bandwidth = "100Mbps"
connections = 50

[[tests]]                     # runs in CI
application = "terraform"
destination = "api.production.example.com:443"
expect = "allow"
Explain a denial, offline
$ skimasque policy check production google.com:443 --app terraform
DENY

Reason:
No matching allow rule.

Suggested rule:
  allow terraform google.com:443

More than a rule list

check, test, explain, and learn run locally. Learning mode drafts a policy from observed traffic. validate --strict fails CI when a [match] is too broad. Policies hot-reload on the gateway without dropping tunnels. Full DSL →

Principles

The gateway enforces policy and trusts nothing by default.

A valid tunnel credential alone does not open a tunnel. The gateway itself checks identity, application, destination, policy, and expiry, and all five must allow the request.

Least privilege by default

If no allow rule matches, the request is denied. Nothing is allowed implicitly.

Fail closed

If authentication, authorization, or destination validation can't be established, no tunnel is created.

SSRF floor

An address policy is checked against resolved addresses, so a hostname that resolves to a blocked address is still blocked.

Keeps working during an outage

A cached policy lets the gateway keep enforcing when the control plane is unreachable. Credentials are verified locally, with no network call.

Policy separate from transport

The policy engine is a pure function and knows nothing about MASQUE or HTTP.

No networking expertise needed

You answer three questions: who is running, what application, and what it needs to reach.

Built on open standards

MASQUE over HTTP/3, written in Rust.

The transport implements the IETF MASQUE specifications on quinn and h3. A SOCKS5 front end lets existing tools use it without changes. The gateway also includes in-process ACME (Let's Encrypt) and Prometheus /metrics, /healthz, and /readyz endpoints.

Open source and SkiMasque Cloud

The enforcement edge is open source, with no features held back.

The open-source gateway does full policy enforcement, including deny-by-default and the SSRF floor, and keeps enforcing if the control plane goes down. SkiMasque Cloud is the paid service that operates the control plane for you.
